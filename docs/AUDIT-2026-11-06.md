## 1. Executive summary

The codebase is substantial and structurally sane: ~14.5k lines of application code, 6 platform adapters, an AI matching/resume/cover-letter layer, a Flask dashboard, bots, and **335 tests, all passing** (`uv run pytest -q` → `335 passed in 22.49s`). The Ego Lite bridge is real and working against the installed macOS build (I ran the binary: `ego-browser nodejs` responds, Node v24.22.1, skill guide v2.2.0).

But **as it sits today, this app cannot do the job you described**, and it is not fast:

1. **It is not set up for you at all.** No `.env`, no `~/.job-agent/`, no database, no master resume, no real profile. The only profile is `config/profiles/example.yaml` — *"Senior Python Developer"*, Python/Django/FastAPI skills, US locations, $150k minimum — and three standalone scripts hardcode that exact file. Your actual background is a Jakarta-based design/frontend engineer (React, Next.js, TypeScript, 4–6 yrs, 15K+ user SaaS). Searches would target the wrong jobs and generated documents would describe the wrong person.
2. **It cannot run end-to-end yet.** Ego Lite is disabled (`ego.enabled: false`), all 5 enabled boards are Playwright/Camoufox/CDP, and the Ego driver's `apply()` is a stub that always returns `False` (`src/job_agent/platforms/ego/driver.py:71-81`). Ego discovery is LinkedIn-only and rejects other platforms.
3. **"Auto-fit" is shallow.** Cover letters and cold emails are generated from `build_candidate_summary()`, which is literally *target role + experience level + a list of skill strings* (`orchestrator/pipeline_steps.py:192-205`) — no work history, no achievements, no portfolio, no job description in the cold-email prompt. The resume-tailoring prompt hardcodes section names that do not exist in your resume.
4. **It is slow by construction.** Fully synchronous; per-card 1.5–2.5 s sleeps, per-character typing at ~120 ms, a `COMMIT` and a `SELECT` per job, a brand-new browser per platform, master-resume re-parsing and a remote Google Fonts fetch on every PDF, and an AI "match budget" that also counts document-generation calls. An hourly scheduler with no wall-clock cap can pile runs on top of each other.
5. **No spreadsheet integration, no JobStreet/SEA boards, no part-time filter, no AI-training gigs.** There is exactly one `import csv` in the whole repo (a one-way CSV export). `JobPosting` has no `employment_type` field. `remote` is a single boolean.
6. **Safety/correctness bugs that matter for real applications:** `debug=True` on a Docker-published dashboard with no auth/CSRF, dry-run writes fake `APPLIED` rows, daily application caps are dead config, `applied_at` is never written, and several applicators return success without verifying a confirmation.

**Verdict:** strong skeleton, but it needs a Phase 0 (make it safe + honest), a Phase 1 (make it fast + wire Ego Lite properly + spreadsheet), then Phase 2/3 (real personalization + coverage). Do **not** turn on auto-apply until P0 items are fixed.

## 3. What is actually in the code

**Runtime:** one CLI (`job-agent = job_agent.main:cli`, `pyproject.toml:29`), Flask dashboard + APScheduler `BlockingScheduler` (60-min interval), daemon threads for dashboard actions, Telegram/Discord bots, SQLite via SQLAlchemy 2.0. Dockerfile/compose run the dashboard (dev server). No FastAPI, no Celery/Redis, no worker queue. `aiohttp` is declared but never imported; no `async def`/`await`/`asyncio` anywhere in `src/`.

**Pipeline** (`orchestrator/pipeline.py:363-548`):
`profile → for each platform: BrowserManager/EgoDriver → login → keywords × locations search (limit 25 each) → dedup (1 SELECT per posting) → detail fetch → AI match → decide (auto_apply ≥0.90 / queue ≥0.70 / skip) → tailor resume PDF + cover letter → driver.apply() → optional cold-email draft → COMMIT`.
Then a separate pass applies `APPROVED` jobs, launching **another browser per platform** (`pipeline.py:203`).

**Adapters:** `linkedin`, `indeed`, `glassdoor`, `ziprecruiter`, `dice`, `wellfound` — each `driver/discovery/applicator/selectors`. `platforms/external_ats.py` (937 lines) handles Greenhouse/Lever/Ashby plus a generic 12-step form loop, Workday and ~9 others fall into generic. Browser = Playwright sync + Camoufox anti-detect + CDP into a human Chrome; `browser/stealth.py` spoofs `navigator.webdriver`, WebGL, plugins.

**AI:** 5 providers (`ai/client.py`), default Gemini, synchronous `httpx.Client(timeout=60)`, 3 retries, Groq 4 s throttle. Match → resume → cover letter → screening → cold email prompts in `ai/prompts.py`. No LLM response cache, no token/cost accounting (tokens are only logged at debug), no budget beyond `max_ai_calls_per_run` (default 20).

**Data:** 6 tables (`db/models.py`); only `jobs.external_id` indexed; **zero Alembic revisions** — schema is `create_all()` + hand-written `ALTER TABLE` with swallowed errors (`db/session.py:46-73`).

## 5. Speed: where the time goes (estimate, not a benchmark)

Assume the example profile (3 keywords × 3 locations), 5 enabled platforms, 25 results per search, and a fully logged-in session:

| Stage | Current behaviour | Estimated cost |
|---|---|---|
| Discovery | 45 searches × 25 cards; LinkedIn authenticated view clicks + sleeps 1.5–2.5 s per card | ~30–45 min of pure sleeping across platforms |
| Dedup / DB | 1 `SELECT` + 1 `COMMIT` per posting (up to ~1125) | thousands of SQLite round-trips |
| LLM | up to 20 calls/platform = 100 calls, serial, 3 retries, 4 s Groq throttle, 60 s timeout each | ~5–20 min, unbounded on retries |
| Documents | master PDF re-parsed + remote font fetch + PDF render per application | seconds each, per job |
| Browsers | 1 new browser per platform + 1 per approved batch | ~10 launches/run |
| Schedule | `BlockingScheduler` every 60 min, no wall-clock cap, no `max_instances`/`coalesce` | overlapping runs possible |

**Target:** one full run under ~10 min with warm sessions. Biggest wins, in order: (1) remove per-card detail clicks/sleeps, (2) parallelise platforms + batch DB I/O, (3) cache LLM/resume/font work, (4) shortlist before detail fetch, (5) hard run timeout. Add stage timings to `AgentRun` — there is currently no instrumentation, so "fast" cannot be measured or regressed.

## 6. Ego Lite: verified state and the right architecture

Verified on this machine:
- `/Applications/ego lite.app/.../Versions/0.6.2.8/Helpers/ego-browser` exists; `Current -> 0.6.2.8` symlink exists.
- `ego-browser --help` lists `nodejs -e <script>` / `nodejs < script.js`; `ego-browser nodejs -e ...` returned `__RESULT__{"node":"v24.22.1","ok":true}` — the `__RESULT__` protocol in `platforms/ego/client.py` is correct.
- Installed skill guide v2.2.0 (macOS) documents `taskSpace`, `page.snapshot`, `page.fetch`, `setInputFiles`, `handOff()`, `waitForControl()`, `finish()`, `page.cdp()`. Quick-start docs explicitly recommend job-hunting with a **stop-before-submit** boundary and human takeover for sign-in/verification.

So the bridge design is sound — the app just uses ~10% of the API. Recommended split:

- **Ego Lite = the interactive, signed-in, human-supervised lane:** discovery on any board via snapshots/semantic selectors, login/2FA/CAPTCHA via `handOff()`, resume upload via `setInputFiles()`, final submit approval via `waitForControl()`, clean up with `finish()`.
- **HTTP/JSON/RSS feeds = the fast lane:** public job APIs and LinkedIn's guest endpoint for bulk listing + dedup, no UI cost.
- **Playwright/Camoufox = fallback** for boards with no usable feed, kept behind conservative rate limits.

Also: one `nodejs` process is spawned per `EgoClient.run()` with a 180 s timeout — batch several jobs into one script and reuse a single task space per run, or the "fast" lane will be slower than Playwright.

## 8. Spreadsheet design

Make the sheet the **human-facing source of truth**, not a second database:

- `Jobs` — `external_id | platform | title | company | location | employment_type | remote_policy | timezone | salary/rate | url | discovered_at | score | match_reason | status | decision | notes`
- `Applications` — `job_key | applied_at | resume_version | cover_letter_version | email_subject | email_body | channel | confirmation | follow_up_at | outcome`
- `Search Profiles` — keywords, locations, employment types, min rate, exclusions, enabled boards (editable by you, read by the agent)
- `Gigs` — network (Alignerr/…), track, hourly rate, assessment status, eligibility, next action

Implementation: a `SheetSync` service with a service-account Google Sheets client (or local `.xlsx` via `openpyxl` for offline use), **idempotent upsert keyed by `external_id + platform`**, batched reads/writes, incremental sync with a watermark, and a "decision" column (`approve` / `reject` / `skip`) that the pipeline reads before submitting — turning the sheet into the human approval gate. Keep SQLite as the operational store; the sheet is the mirror + control surface. Add CSV/XLSX export from the same service.

## 12. One honest caveat

Automating applications on LinkedIn/Indeed/JobStreet sits against most platforms' terms of service, and this repo deliberately includes anti-detection code. No amount of engineering removes that risk. The design that is both fastest and safest is: **feeds/APIs for discovery, Ego Lite with your own signed-in session for the interactive parts, a spreadsheet as the approval surface, and a human confirmation on the final submit.** That also happens to be the design that produces better applications than blind auto-apply.
